# Security Policy

The Williams team takes the security of our smart contracts and protocol infrastructure seriously. As a protocol managing trustless inheritance and user funds on Stellar Soroban, we encourage responsible disclosure of any security vulnerabilities.

---

## Supported Versions

Only the latest code on the `main` branch and currently active deployments are actively supported for security updates:

| Version / Deployment | Supported | Notes |
| -------------------- | --------- | ----- |
| `main` branch        | :white_check_mark: | Primary codebase |
| Stellar Testnet      | :white_check_mark: | Deployed contract ID in [`deployments/testnet.json`](./deployments/testnet.json) |
| Older releases/tags  | :x: | Unsupported |

## Reporting a Vulnerability

**Do not report security vulnerabilities via public GitHub issues, discussions, or pull requests.**

If you discover a security vulnerability, please report it privately using one of the following methods:

1. **GitHub Private Vulnerability Reporting (Preferred)**:
   - Navigate to the [Security Advisories](https://github.com/willi-d7/williams-contracts/security/advisories) tab of the canonical repository (`willi-d7/williams-contracts`, matching the `repository` field in [`contracts/will/Cargo.toml`](./contracts/will/Cargo.toml)).
   - Click **"Report a vulnerability"** to submit a confidential report directly to the maintainers.
   - **Maintainer note**: Private Vulnerability Reporting must be verified as enabled for the canonical repository before this channel is advertised. Verify with read-only checks of the repository's security settings and links only; do not submit a test disclosure.

2. **Email Disclosure (Reviewed Fallback)**:
   - If Private Vulnerability Reporting is unavailable for the canonical repository, send your findings to `security@williams.org`. This is the reviewed fallback channel.
   - Include a detailed description of the vulnerability, steps or proof-of-concept (PoC) code to reproduce it, and the potential impact on user funds or contract execution.

### Expected Response SLAs

- **Initial Acknowledgment**: Within **48 hours** of receiving your report.
- **Triage & Assessment**: Within **5 business days**, detailing validity, severity classification, and expected remediation timeline.
- **Fix & Public Disclosure**: Fixes will be coordinated and deployed prior to any public advisory release.

## Safe Harbor & Responsible Disclosure

If you conduct security research in good faith and follow these guidelines, we will:

- Consider your research to be authorized and refrain from taking legal action against you.
- Work with you to understand and remediate the issue promptly.
- Recognize your contribution in our security advisories and reward pool (where applicable).

### Rules of Engagement

- **Do not compromise user funds**: Test vulnerabilities against local Soroban test environments or mock data on Testnet. Do not attempt to drain live contract instances.
- **Maintain confidentiality**: Keep information about discovered vulnerabilities private until a fix has been released and coordinated disclosure is agreed upon.
- **Avoid disruptive testing**: Do not perform Denial of Service (DoS) attacks, spam transactions, or social engineering against maintainers.

## Known Risks & Mitigations

### Replay of `reveal_and_claim` (#440)

A hashed beneficiary claims by revealing a pre-image of the commitment stored
on the will. That pre-image is public once the claim transaction is submitted,
so without extra checks an observer could replay it or front-run it. The
contract mitigates this as follows:

- **One claim per slot.** Each hashed slot has a `claimed` flag, which is set
  and persisted in the same invocation that pays out, before the token
  transfer. Any later call for that slot fails with `AlreadyClaimed`.
- **Pre-image bound to the recipient.** The first 32 bytes must match
  `sha256(xdr(claimant))`, and `claimant` must authorize the call.
- **Signed invocations cannot be replayed.** Soroban authorization entries
  carry a nonce and an expiration ledger.

#### Constructing a hashed commitment

Serialize the beneficiary address as a Stellar `ScVal::Address` in XDR.
Hash those bytes with SHA-256, then append exactly 32 bytes generated by a
cryptographically secure random number generator. Register the SHA-256
digest of that 64-byte pre-image with `add_hashed_beneficiary`. Keep the
salt until the claim, and pass the 64 raw bytes to `reveal_and_claim`.

The earlier `sha256(xdr(address) || salt)` recipe is incompatible with the
verifier. It requires the address **digest** in the first 32 bytes.

```rust
use soroban_sdk::{xdr::ToXdr, Address, Bytes, BytesN, Env};

fn hashed_commitment(env: &Env, beneficiary: &Address, salt: &BytesN<32>) -> (Bytes, BytesN<32>) {
    let address_xdr = beneficiary.clone().to_xdr(env);
    let mut preimage: Bytes = env.crypto().sha256(&address_xdr).to_bytes().into();
    preimage.append(&salt.into());
    let commitment = env.crypto().sha256(&preimage).to_bytes();
    (preimage, commitment)
}
```

```js
import { Address } from "@stellar/stellar-sdk"; // v16
import { createHash } from "node:crypto";

function hashedCommitment(beneficiary, salt) {
  if (salt.length !== 32) throw new RangeError("Expected 32 salt bytes");
  const sha256 = bytes => createHash("sha256").update(bytes).digest();
  const addressXdr = new Address(beneficiary).toScVal().toXDR();
  const preimage = Buffer.concat([sha256(addressXdr), salt]);
  return { preimage, commitment: sha256(preimage) };
}
```

Both vectors use the public test salt
`000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f`.
Append its decoded bytes to the decoded fingerprint to obtain the pre-image.
Generate fresh random salt for each real commitment.

### Fee-on-Transfer and Deflationary Tokens (#39)

Williams assumes that all deposited tokens adhere to standard SEP-41 semantics without deduction on transfer (`balance_transferred == amount`).

- **Threat Model**: If a deflationary or fee-on-transfer token is deposited via `create_will` or `top_up`, the actual tokens received by the contract will be strictly less than the nominal `amount` recorded in the will's internal balance. When `distribute()` attempts to pay out beneficiaries or `cancel_will()` refunds the owner, the contract will attempt to transfer more tokens than it holds, causing the transaction to revert and trapping the remaining funds.
- **Mitigation**: Users and integrators must only deposit standard 1:1 SEP-41 tokens without transfer fees. Tokens with burn-on-transfer, fee-on-transfer, reflection, or rebasing mechanisms are unsupported.
